# オリジナルAI プロジェクト構造設計書 v0.1 への技術レビュー

**レビュー対象:** `original_ai_project_structure.md` v0.1（設計案）
**レビュー日:** 2026-08-03
**反映先:** `docs/original-ai/project-structure.md`（v0.2）

---

## 総評

**骨格は正しい。** 二層分離・レビュー優先ゲート・トレース計装という3本柱は、個人が高リスク領域（法律実務・生徒データ）でAIを常用するための正しい選択で、この3つを最初から設計に入れている点は評価できる。

一方で、**v0.1 のまま実装に入ると3つの理由で頓挫する可能性が高い**。

1. **真実源が二重化している。** `SKILL.md` と `registry/skills.jsonl` の両方に version・budget・gates を書く設計になっており、必ずずれる。そのずれを直すために `drift-audit` が要る、という自作自演の構造になっている。
2. **安全機構より先に高リスクスキルを移植する順序になっている。** ロードマップ上、`gas-automation`（risk: high、外部作用あり）の移植が P2、ゲート実装が P4。ゲートのない状態で高リスクスキルを新基盤に載せる期間が生じる。
3. **出力品質のテストが一つもない。** 費用・トレース・スキーマの回帰テストは充実しているが、「条文番号を間違えた答弁書」「生徒の得点を取り違えた面談資料」はどのテストにも引っかからない。法律・教育ドメインで最も高い実損リスクが無防備。

以下、重大度順に18件。各項目は **現状 → 問題 → 推奨** の形式。

---

## S. 重大（実装前に必ず解決すべき）

### S1. 台帳とSKILL.mdの二重管理 → 台帳を生成物にする

- **現状:** §3.1 で `skills.jsonl` に `version` `budget` `gates` `triggers` を持たせ、§5 で同じ情報を `SKILL.md` のフロントマターと本文にも書いている。書き込み権限を2スキルに絞る運用でカバーする設計。
- **問題:** 権限を絞ってもずれる。人間が `SKILL.md` を直して台帳を忘れる、あるいは逆が必ず起きる。§8 の `drift-audit` はこのずれを検出するための仕組みだが、**そもそもずれない設計にすれば不要**。二重化を残したまま監査で守るのは、コストの高い解法。
- **推奨:** `SKILL.md` のYAMLフロントマターを**唯一の真実源**とし、`registry/skills.jsonl` は `scripts/build_registry.py` が生成する**ビルド成果物**にする。CI で「生成し直して差分が出たら fail」を1行入れれば、ドリフトは構造的に発生しない。`drift-audit` は台帳整合ではなく「versions/ のスナップショットと作業ツリーの乖離」という本来の役割に専念させる。

### S2. 決定論的ルーターは劣化要因 — モデルネイティブな選択に寄せる

- **現状:** §4.2 `router.py` が `triggers` のキーワード＋埋め込みマッチで上位N件を返す。
- **問題:** (a) `triggers` 語彙のメンテが永久に続く（新しい言い回しのたびに台帳修正）。(b) キーワードに引っかからなかった正解スキルは候補にすら上がらず、**モデルが本来持っている選択能力を下回る**。(c) 既存のスキル群は既に「descriptionにトリガー語を列挙し、モデルが読んで選ぶ」方式（Agent Skills の progressive disclosure）で動いており、それを捨てて自前ルーターを作るのは退行。
- **推奨:** 一次選択はモデルに委ね、ルーターは**フィルタとしてのみ**使う。具体的には `router.py` の責務を「候補を選ぶ」から「選ばれた候補を検証する」に反転させる：
  - 台帳から `stage: deprecated` / 予算枯渇 / 権限不足のスキルを**候補から除外**する
  - 選択されたスキルが `depends_on` を満たすか検査する
  - 高リスクスキルが選ばれたら理由の明示を要求する
  埋め込み検索はスキル数が50を超えてから、description の全文投入がコンテキストを圧迫し始めた時点で導入すれば足りる（progressive disclosure なら数百スキルまで持つ）。

### S3. `plan.json` 凍結は現実の作業に合わない — 境界を「権限」に置き換える

- **現状:** §4.3「`plan.json` は確定してから実行層に渡す。推論層は途中で書き換えない」「実行中の再計画は InterruptedError で推論層に戻る明示的な再入口経由」。
- **問題:** 実務タスクは1発で計画が確定しない。答弁書ドラフトなら「証拠を読む → 争点が変わる → 参照すべき判例が変わる」。この設計だと **InterruptedError 経由の再入口が例外ではなく常態**になり、そのたびに plan 全体を作り直すのでトークンを二重に払う。厳格な計画凍結は、ステップが機械的に確定するバッチ処理向けの構造。
- **推奨:** 二層分離の本質は**計画の凍結ではなく権限の分離**。以下に組み替える。
  - 推論層のプロセスには **書き込み系・ネットワーク系のツールを物理的に渡さない**（Read/Grep/Glob のみ）。これは `.claude/settings.json` の permissions と、実行層プロセスの capability 制限の両方で担保する。
  - 計画は**追記可能なログ**（`plan_log.jsonl`）にし、`revision` を持たせる。再計画は例外ではなく正常系のイベントとして記録する。
  - 凍結すべきは plan 全体ではなく **「承認済みのステップ」**（→ S4）。
  - 予算はプラン単位ではなく**セッション単位の残高**で管理する。再計画が正常系になる以上、プラン単位の上限は無意味になる。

### S4. 承認のTOCTOU — 承認は内容ハッシュに束縛する

- **現状:** §6.1 `HookResult.WAIT_FOR_APPROVAL(gate)` を返すのみ。承認状態がどこに保存され、いつ失効し、何に対する承認なのかが未定義。
- **問題:** 承認を得た後に入力が差し替われば、**承認済みフラグだけが残って別物が実行される**。「答弁書のドラフトAを見て送信を承認 → 再生成でBになった → Bが送信される」。外部送信・法的提出物ゲートを持つ設計でこれは致命的。
- **推奨:** 承認レコードを独立したストアに持ち、**承認対象の内容ハッシュに束縛**する。
  ```json
  {
    "approval_id": "uuid",
    "scope": "step",                       // plan | step | tool_call
    "target_hash": "sha256:...",           // 承認時点の inputs+outputs の正規化ハッシュ
    "gate": "external-send",
    "approver": "user",
    "granted_at": "2026-08-03T22:10:00+09:00",
    "expires_at": "2026-08-03T23:10:00+09:00",
    "one_shot": true
  }
  ```
  実行直前に `target_hash` を再計算して一致しなければ**承認を無効化して再承認を要求**する。`expires_at` 既定は1時間、`one_shot: true` が既定。「今後すべて許可」は作らない（作るなら gate 単位＋期限つきで、`destructive-ops` と `legal-submission` は対象外）。

### S5. ゲート・予算のフェイルセーフ方向が未定義

- **現状:** `budget_guard.check()` が false を返したらブロック、とのみ。状態ストアの読み書きが失敗した場合、ゲート実装が例外を投げた場合の挙動が未定義。
- **問題:** 実装によっては「例外 → 握りつぶし → PROCEED」になりがちで、安全機構が沈黙して無効化される。これが最悪の故障モード（壊れていることに気づけない）。
- **推奨:** **fail-closed を明文化**する。ゲート評価・予算照会が例外・タイムアウトで結論を出せない場合は `BLOCK` を返す。加えて `tests/governance/test_fail_closed.py` で「ストアを壊した状態で高リスク操作が通らないこと」を回帰テストする。日次予算カウンタは複数プロセスからの同時更新があり得るので、**アトミックな加算**（SQLite のトランザクション、またはファイルロック）にする。JSONファイルの read-modify-write は競合で必ず取りこぼす。

### S6. 個人情報・秘匿情報の分類が設計に存在しない

- **現状:** §9 でトレースに `inputs_hash` / `outputs_hash` を記録、30日ローテート。`artifacts/` は Dropbox 同期。
- **問題:** 扱う対象が **訴訟事件記録（相手方・依頼者情報）と塾生徒（未成年）の成績・連絡先**。この2種を扱う基盤で、データ分類・保持期間・同期先の扱いが設計に一言もないのは穴。特に `artifacts/` の Dropbox 同期は、事件記録が第三者サービス上に平文で載ることを意味する。
- **推奨:**
  - `SKILL.md` フロントマターに `data_class: public | internal | pii | privileged` を必須化。
  - トレースには**本文を書かない**（ハッシュ＋artifacts へのポインタのみ）を明文化し、`pii` / `privileged` のスキルは `artifacts/` 内の分離ディレクトリ（同期対象外）に出力する。
  - 保持期間をクラス別に定義（`internal` 30日 / `pii` 90日で削除 / `privileged` は削除せず別管理）。
  - `.gitignore` だけでなく **CI の secret scanning + PII パターン検査**を入れる（`traces/` `artifacts/` を誤コミットした瞬間に落とす）。

## M. 中程度（v0.2 で直すべき）

### M1. `common/` 全面禁止は行き過ぎ — 「スキル間結合」と「純粋ライブラリ」を分ける

- **現状:** §10 非目標「共通ユーティリティ層は作らない（メタスキル化する）」。
- **問題:** JSON Schema 検証・ハッシュ計算・トレース書き出し・日付パースまでメタスキル経由にすると、**純粋関数1回のためにLLM往復が発生**し、レイテンシもコストも桁で悪化する。独立性が守りたいのは「スキルAの判断ロジックがスキルBに依存すること」であって、「共通のutilを使わないこと」ではない。
- **推奨:** 2種類に明確に分ける。
  - **`origin_core/`（純粋ライブラリ・依存OK）** — スキーマ検証、トレースクライアント、ハッシュ、予算クライアント、モデル呼び出しラッパ。副作用を持つ判断は入れない。バージョン管理は pyproject の依存として行う。
  - **メタスキル（判断を含む・台帳経由）** — `fact-check-guard` のように「LLMの判断」が入るもの。
  - lint で禁止するのは `skills.* → skills.*` の import のみ（`skills.* → origin_core` は許可）。§7.5 の `check_skill_independence.py` はこのルールに書き換える。

### M2. トレースにキャッシュ階層とモデルIDがない → コストが必ず狂う

- **現状:** §7.4 トレーススキーマの必須項目は `tokens_in` / `tokens_out` / `cost_usd`。
- **問題:** プロンプトキャッシュを使うと入力トークンは **通常入力・キャッシュ書き込み（割高）・キャッシュ読み出し（大幅割安）** の3種に割れる。1つの `tokens_in` に潰すとコスト計算が実態から乖離し、しかも**キャッシュ最適化の効果が測定できない**（費用計装の主目的が達成できない）。モデルIDがないと単価も引けない。
- **推奨:** 必須項目に以下を追加。
  `model_id`, `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`, `prompt_hash`, `cache_hit_ratio`, `data_class`, `approval_ref`, `retry_count`, `error_class`
  `cost_usd` は生の値ではなく `pricing/models.json`（単価表・改定日つき）を参照して算出し、**単価表のバージョンもトレースに残す**（あとから遡って再計算できるようにする）。

### M3. トークン回帰テストがモックLLMでは成立しない

- **現状:** §7.2 `test_token_regression` が `mock_llm` の下で `result.tokens_in` を黄金値と比較。
- **問題:** モックはトークンを数えない。実装すると「モックが返す固定値と黄金値を比べる」空テストになる。
- **推奨:** 入力側と出力側を分ける。
  - **入力トークン:** 実際にプロンプトを組み立て、**トークンカウントAPI（`count_tokens`）または同一トークナイザ**で数える。モデル呼び出しは発生しないので安価かつ決定的。これは厳密な閾値（黄金値 +10%）で守れる。
  - **出力トークン:** 非決定的なので等値比較は不可能。**上限（`max_tokens` と実測の分布）**のみを検査する。
  - 黄金値ファイルには**測定日と単価表バージョン**を持たせ、モデル更新時に一括更新できるようにする。

### M4. `test_chain_replay` のハッシュ一致は達成不能

- **現状:** §7.3「過去のトレースから plan.json を復元し、同一入力で同一出力になる」を `outputs_hash` の等値で検査。
- **問題:** temperature 0 でも LLM 出力のバイト等値は保証されない。このテストは恒常的に赤になり、やがて無視されるか削除される（＝計装への信頼が壊れる）。
- **推奨:** 再実行性の検査対象を分割する。
  - **実行層のみのステップ（純粋な手続き）:** ハッシュ等値で検査してよい。
  - **推論を含むステップ:** 記録済みレスポンス（カセット方式）を差し込んで**制御フローの再現**（同じステップ列・同じゲート発火・同じ予算消費）を検査する。生成テキストは**スキーマ準拠と必須要素の存在**という意味的不変条件で検査する。

### M5. Hooks の粒度が Claude Code の実際の機構と噛み合っていない

- **現状:** §6.1 の擬似コードが `PlanStep` を引数に取る。
- **問題:** Claude Code の Hooks は**ツール呼び出し単位**で発火し、stdin に JSON を受け取り、終了コード（PreToolUse は 2 でブロックし stderr をモデルに返す）で判定する機構。`PlanStep` は渡ってこない。このまま実装すると、対話セッション側では policy が効かず、バッチ実行側だけで効く（あるいはその逆）という**穴のあるガバナンス**になる。
- **推奨:** **ポリシーを単一モジュール `policy/` に置き、2つの入口から呼ぶ。**
  - `.claude/hooks/pre_tool_use.py` — 対話セッション用アダプタ（stdin JSON → policy → exit code）
  - `orchestrator/middleware.py` — バッチ実行用アダプタ（PlanStep → policy → HookResult）
  こうすれば「どちらの経路でも同じルールが効く」ことをテストで担保できる。§7 に `tests/governance/test_policy_parity.py`（両アダプタが同じ入力に同じ判定を返す）を追加する。

### M6. SemVer の刻み方が未定義（プロンプトを含む成果物特有の問題）

- **現状:** `version: 1.4.2` とあるが、何をもって major/minor/patch とするかが未定義。
- **問題:** プロンプト文を1文直しただけで major が上がったり、逆に出力形式を変えたのに patch で済まされたりする。`depends_on: meta.fact-check-guard >= 1.0.0` のような依存指定が意味を失う。
- **推奨:** **契約の変更＝major** と定義する。
  - **major:** inputs/outputs スキーマの破壊的変更、gates の削除、権限拡大
  - **minor:** 入力の任意項目追加、gates の追加、能力の追加
  - **patch:** プロンプト文言・内部実装の変更で、契約と eval 合格ラインが不変のもの
  `stage` の昇格（experimental → beta → stable）は**eval 合格率で門番**する（→ G1）。人間の感触だけで stable にしない。

## G. 欠落（設計に項目そのものがない）

### G1. 出力品質の評価（evals）がない ← **最大の穴**

- **問題:** テスト階層（Unit / Cost / Trace / Integration / Governance）はすべて**形式**の検査で、**中身の正しさ**を見るものが一つもない。この基盤で最も損害が大きい故障は「予算超過」でも「トレース欠損」でもなく、**自信満々に間違った条文を引いた書面**と**取り違えた生徒データに基づく面談資料**。
- **推奨:** `evals/` を第一級のディレクトリとして追加する。
  - スキルごとに固定の評価セット（入力＋期待される要素／禁止される要素）
  - 採点は「決定的チェック（引用条番号の実在、数値の一致、必須節の有無）」を先に、「LLM-judge によるルーブリック採点」を後に。judge の合意率を人手サンプルで定期検証する
  - `stage` 昇格と `version` の major/minor リリースを**eval 合格率の閾値でゲート**する
  - CI では低コストの決定的チェックのみ、judge を含む全量は日次で回す

### G2. 秘密情報（APIキー・認証情報）の扱いが未定義

- **問題:** 外部API・LINE通知・Dropbox 同期を前提にしながら、キーの保管場所・スキルへの渡し方・トレースへの混入防止の規定がない。トレースに `inputs_hash` しか残さない設計でも、**エラーメッセージ経由で平文が漏れる**のが典型的な事故。
- **推奨:** キーは環境変数または OS キーチェーンのみ、`SKILL.md` に `secrets: [LINE_TOKEN]` と宣言したものだけを実行層が注入、トレース書き出し時に**宣言済みシークレット値のマスキング**を強制。CI に secret scanning。

### G3. 冪等性・リトライ・部分失敗の扱いがない

- **問題:** `plan.json` の途中でステップが失敗したときの挙動（巻き戻すのか、再開するのか、成果物が半端に書かれた状態をどう扱うのか）が未定義。外部送信を含むステップのリトライは**二重送信**を意味する。
- **推奨:**
  - すべてのステップに `idempotency_key`（`plan_id` + `step_id` + `inputs_hash`）を持たせ、実行層は同一キーの完了済みステップをスキップする
  - ファイル出力は一時ファイル＋アトミック rename（半端な成果物を作らない）
  - 外部作用のあるステップは**自動リトライ禁止**（人間の再承認を経由）

### G4. 既存スキル群からの移行コストが見積もられていない

- **問題:** ユーザーは既に多数のスキルを運用中。v0.1 は「新契約に書き換えてから移植する」前提だが、全スキルを一斉に書き換えるのは現実的でなく、移行期間中に**新旧2つの運用が並走**する。
- **推奨:** **シム（互換層）を先に作る。** `adapters/legacy_skill.py` が、拡張フィールドを持たない既存 `SKILL.md` を読み込み、欠損フィールドに保守的な既定値（`risk: high`, `stage: experimental`, `gates: [all]`, 低予算）を補って動かす。これで既存スキルは**無改変で新基盤に載り**、価値の高いものから順に契約を書き足していける。ビッグバン移植を避けるのが完走の条件。

### G5. 「モデル非依存」と実装の実態が矛盾

- **問題:** §10 非目標「モデル固有機能への依存をしない」と掲げつつ、`.claude/`・Hooks・Subagents という Claude Code 固有の機構に全面的に乗っている。この矛盾を放置すると、移植性のために設計が歪む割に実際には移植できない、という最悪の両取りになる。
- **推奨:** **正直に一次ランタイムを Claude Code に決める。** その上で移植性は「`skills/` 配下（SKILL.md + scripts + prompts）はランタイム非依存の素の Markdown と Python に保つ」という**限定した約束**に落とす。ランタイム固有の接着剤は `adapters/claude_code/` に隔離し、そこだけ差し替えれば他ランタイムに載る構造にする。

## R. ロードマップの順序修正

v0.1 のフェーズ順は **安全機構より先に高リスクスキルが載る**。並べ替えを推奨。

| v0.1 | 内容 | 問題 |
|---|---|---|
| P2 | 実務スキル移植（`gas-automation` risk:high を含む） | ゲート未実装の状態で外部作用スキルが載る |
| P3 | 費用・トレース計装 | 移植後に計装 → 移植期間中の消費が見えない |
| P4 | ゲート実装 | 遅すぎる |

**推奨順:** 骨格 → **安全床（ゲート・予算・トレース）** → メタスキル → 低リスク実務スキル → eval → 高リスク実務スキル → User Mirror → 分散実行。
「ゲートを通らずに外部作用が起きないこと」をテストで確認するまで、`external-send` を持つスキルは新基盤に載せない。
