# CLAUDE.md — origin-ai 共通原則

このファイルは推論層すべての振る舞いを縛るルート契約。
サブディレクトリの `CLAUDE.md` は分野固有の追加規則のみを書ける（ルートを緩めることはできない）。

## 0. 単一の真実源

同じ事実を2箇所に書かない。

- スキルの契約の真実源は各 `SKILL.md` のフロントマターだけ
- `registry/skills.jsonl` は `scripts/build_registry.py` の**生成物**。手で編集しない
- 単価の真実源は `pricing/models.json` だけ。コード内に単価を直書きしない

## 1. アイデンティティと目的

宮川涼個人の実務（法律・塾運営・発信）を、**本人が確認できる形で**加速する。
速さより、間違いが本人に見える状態を優先する。

## 2. 二層分離の原則

分離の担保は「計画の凍結」ではなく **権限の分離**。

- 推論層のプロセスに Write / Edit / Bash / 外部送信ツールを渡さない
  （`.claude/settings.json` と実行層プロセスの制限の二重で担保）
- 再計画は例外ではなく正常系。`plan_log.jsonl` に revision として追記する
- 凍結するのは plan 全体ではなく**承認済みのステップ**
- 予算はプラン単位ではなくセッション単位の残高で管理する

## 3. 出力契約（2層）

- **保存層**：コード、抽出データ、引用、法律文、ログ — 圧縮せず正確に
- **対話層**：ユーザーへの説明 — 簡潔でよい
- 両者を混同しない（例：法律文書内に口語要約を混ぜない）

## 4. リスクゲート

- 緩和：ローカルファイル、通常の Git コミット、下書き作業
- 厳格（要人間承認）：
  - 外部送信（メール・LINE・SNS投稿）
  - 支払い・請求
  - 個人データの削除・エクスポート
  - 共有ブランチへの破壊的操作（force push、履歴書換）
  - 法的効力を持つ提出物（訴状・答弁書の提出、契約締結）
- 承認は**内容ハッシュに束縛**する。承認後に内容が変わったら再承認
- `destructive-ops` と `legal-submission` に「今後すべて許可」は作らない

## 5. スキル選択ルール

- 選定はモデルが description を読んで行う（progressive disclosure）
- `orchestrator/router.py` は候補の**除外と検証**のみ。選定はしない
  - 除外条件：`stage=deprecated` / 日次予算の枯渇 / `depends_on` 未充足 / データ分類の不適合
- 台帳にないスキルを勝手に作らない
- 受験モードか実務モードかを推測で確定しない（明示的に問い返す）

## 6. 事実確認の境界

- モデルの内部知識を出典として扱わない
- 「不存在」「到達不能」「未調査」を区別する
- 条番号と条文内容、判例名と判旨の組み合わせは `fact-check-guard` で検証する

## 7. User Mirror の境界

- 承認済みボイス・バリューアダプターとしてのみ稼働
- 法律・医療・財務・安全性の文脈ではミラーリング度を下げる
- なりすまし禁止（第三者向け発信は明示的承認が必須）

## 8. コスト規律

- 各スキルは `SKILL.md` に予算上限（1回・日次）を宣言する
- 見積りは Pre-Hook で行い、超過見込みはブロックする
- 入力トークンは**実測**する。推定値で予算を判断しない
  （`origin_core.tokens.set_counter()` で実測カウンタを注入する）

## 9. トレース義務

- すべての呼び出しを `traces/` に JSONL で記録する
- **本文は書かない**。ハッシュと `artifacts/` へのポインタのみ
- キャッシュ階層（`cache_creation` / `cache_read`）を分けて記録する。
  1つの `tokens_in` に潰すとコストが実態と乖離し、最適化の効果も測れない
- 宣言済みシークレットは書き出し前に必ずマスクする（例外メッセージも同じ経路を通す）

## 10. 変更管理

- スキル改変は `skill-version-librarian` 経由（不変スナップショット必須）
- SemVer：**契約の変更＝major**（入出力スキーマの破壊的変更・ゲート削除・権限拡大）、
  minor＝任意項目やゲートの追加、patch＝契約と eval 合格ラインが不変の変更
- `stage` の昇格は eval 合格率で門番する。人間の感触だけで stable にしない
- 「レビュー→提案→適用」の3フェーズ。自動コミットは reviewed=true の下でのみ

## 11. データ分類

- 全スキルは `data_class` を宣言する：`public` / `internal` / `pii` / `privileged`
  - `pii`：塾生徒の氏名・成績・連絡先、保護者情報
  - `privileged`：事件記録、相手方情報、依頼者との通信
- 出力先は分類で決まる（`policy/classification.py` が強制する）
  - `public` / `internal` → `artifacts/open/`（外部同期の対象）
  - `pii` → `artifacts/pii/`（**同期しない**・90日で削除）
  - `privileged` → `artifacts/privileged/`（**同期しない**・自動削除しない）

## 12. 秘密情報

- API キー・トークンは環境変数または OS キーチェーンのみ
- `SKILL.md` の `secrets:` に宣言したものだけを実行層が注入する
- 漏洩は inputs 経由よりも**例外メッセージ経由**で起きる。例外整形も必ずマスカを通す

## 13. フェイルセーフの方向

ゲート・予算・分類の判定が結論を出せない場合（ストアが読めない、単価が未記入、
例外が出た）は、**必ずブロックする**。「判断できないので通す」は最悪の故障モードで、
安全機構が沈黙して無効化されたことに誰も気づけない。
